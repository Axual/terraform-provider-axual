# axual_user (Resource)

User resource. Creating new users via Terraform is not supported. Use the axual_user data source to reference existing users, or use terraform import to manage existing users. Destroying an axual_user, or removing its block, deletes the user in Platform Manager. New users are created by logging in through your organization's SSO provider. Read more: https://docs.axual.io/axual/2026.1/self-service/user-group-management.html#users

~> **Warning:** Destroying an `axual_user`, or removing its block, deletes the user in Platform Manager. The user
leaves every group (as member and as manager). When Platform Manager manages the logins in Keycloak, it also
deletes the user's Keycloak login in the realm that has the tenant's short name. To refer to a user, use the
[`axual_user` data source](https://registry.terraform.io/providers/Axual/axual/latest/docs/data-sources/user). To stop
managing an imported user without deleting it, use a `removed` block with `lifecycle { destroy = false }`
(Terraform 1.7 or later), or `terraform state rm`. See "Stop managing a user" below.

## User creation is not supported

Terraform cannot create users. Users created through the API were only added to Self-Service, not to the
authentication provider (for example Keycloak), so they could not log in. Reference a user with the
[`axual_user` data source](https://registry.terraform.io/providers/Axual/axual/latest/docs/data-sources/user)
(see the example below), or import the user (see Import below).

### Creating new users

New users are created by logging in through your organization's Single Sign-On (SSO) provider. When a user authenticates via SSO for the first time, they are automatically registered in Self-Service.

## Required Roles

- No role is needed to import and read a user.
- TENANT_ADMIN is needed for every change and for delete, also for your own user. Each update also sends the roles,
  and only a Tenant Admin may set roles.

## Schema

### Required

- `email_address` (String) User's email address. It must be the address that Platform Manager has: Platform Manager refuses a change of the email address.
- `first_name` (String) User's first name
- `last_name` (String) User's last name

### Optional

- `middle_name` (String) User's middle name
- `phone_number` (String) User's phone number
- `roles` (Attributes Set) Roles attributed to the user. Leave it out to keep the roles the user has; `roles = []` removes all roles. Valid names: `TENANT_ADMIN`, `APPLICATION_ADMIN`, `APPLICATION_AUTHOR`, `STREAM_ADMIN`, `STREAM_AUTHOR`, `ENVIRONMENT_ADMIN`, `ENVIRONMENT_AUTHOR`, `SCHEMA_ADMIN`, `SCHEMA_AUTHOR`, `BILLING_VIEWER`, and `PLATFORM_ADMIN` from Platform Manager 17.0.0. Only a Super Admin can set `SUPER_ADMIN` and `BILLING_INTERNAL`. Every change of an `axual_user` sends the roles, so it needs TENANT_ADMIN. (see [below for nested schema](#nestedatt--roles))

## Example Usage

### Importing and managing an existing user

```hcl
# First, import the user:
# terraform import axual_user.john b21cf1d63a55436391463cee3f56e393

resource "axual_user" "john" {
  first_name    = "John"
  last_name     = "Doe"
  email_address = "john.doe@example.com"
  phone_number  = "+37253412551"
  roles         = [
    { name = "APPLICATION_AUTHOR" },
    { name = "ENVIRONMENT_AUTHOR" },
    { name = "STREAM_AUTHOR" }
  ]
}
```

### Referencing a user via data source (recommended)

```hcl
data "axual_user" "john" {
  email = "john.doe@example.com"
}

# Use data.axual_user.john.id to reference the user
```

### Stop managing a user

Do not just remove the `axual_user` block: that deletes the user. Replace the block with a `removed` block
(Terraform 1.7 or later). Terraform then forgets the user, and the user stays in Platform Manager:

```terraform
removed {
  from = axual_user.john

  lifecycle {
    destroy = false
  }
}
```

To protect a managed user against a delete, add `lifecycle { prevent_destroy = true }` to its `axual_user` block.

For a full example which shows the capabilities of the latest Terraform provider, check https://github.com/Axual/terraform-provider-axual/tree/master/examples/axual.

## Import

Import is supported by ID, or by email address (`email:`):

```shell
terraform import axual_user.<LOCAL NAME> <USER UID>
terraform import axual_user.test_user b21cf1d63a55436391463cee3f56e393
terraform import axual_user.<LOCAL NAME> email:<EMAIL ADDRESS>
terraform import axual_user.test_user 'email:jane.doe@example.com'
```

Use the email address as Platform Manager shows it: depending on the database, the search can be case-sensitive.
An `import` block (Terraform 1.5 or later) takes the same IDs:

```terraform
import {
  to = axual_user.test_user
  id = "email:jane.doe@example.com"
}
```

In Terraform 1.12 or later, an `import` block can use `identity` instead of `id`:

```terraform
import {
  to = axual_user.example
  identity = {
    id = "b21cf1d63a55436391463cee3f56e393"
  }
}
```
