# axual_application (Resource)

An application is responsible for producing and/or consuming data on a topic, whether it is a Java or .NET app or a connector.

## Platform Manager version

- `application_type = "FLINK_SQL"` needs Platform Manager 16.0.0 or later. The other types work with
  every supported version.
- From Platform Manager 17.0.0, a `Connector`, `Ksml` or `FLINK_SQL` application needs that runtime
  enabled in the tenant settings. A new tenant starts with them off. Existing tenants get them
  enabled on the upgrade.

## Required Roles
- Create: APPLICATION_AUTHOR or APPLICATION_ADMIN
- Change or delete: APPLICATION_ADMIN, or a member of the group that owns the application. When the
  tenant allows only resource managers to update and deploy, you must be a resource manager of that group.

## Features
Axual Terraform Provider supports the Custom, Connector, KSML and Flink SQL application types (`application_type` values `Custom`, `Connector`, `Ksml` and `FLINK_SQL`). Read more: https://docs.axual.io/axual/2026.1/self-service/application-management.html#application-types

## Schema

### Required

- `application_id` (String) The Application ID of the Application, usually a fully qualified class name. Must be unique when the tenant requires unique consumer groups. The application ID, used in logging and to determine the consumer group (if applicable). Read more: https://docs.axual.io/axual/2026.1/self-service/application-management.html#app-id
- `application_type` (String) Axual Application type. Possible values are Custom, Connector, Ksml, or FLINK_SQL.
- `name` (String) The name of the Application. Must be unique. Only the special characters `_`, `-`, `.` and ` ` are valid as part of an application name.
- `owners` (String) Application Owner
- `short_name` (String) Application short name. Unique human-readable name for the application. Only lower case letters, digits and `_`, 3 to 60 characters, not starting with `_`. Must be unique.
- `visibility` (String) Application Visibility. Defines the visibility of this application. Possible values are Public and Private. Set the visibility to “Private” if you don’t want your application to end up in overviews such as the topic graph. Read more: https://docs.axual.io/axual/2026.1/self-service/application-management.html#app-visibility

### Optional

- `application_class` (String) The application's plugin class. Required if application_type is Connector. For example com.couchbase.connect.kafka.CouchbaseSinkConnector. All available application plugin class names, pluginTypes and pluginConfigs listed here- GET: /api/connect_plugins?page=0&size=9999&sort=pluginClass and in Axual Connect Docs: https://docs.axual.io/connect/Axual-Connect/connect-plugins-catalog/connect-plugins-catalog.html
- `description` (String) Application Description. A short summary describing the application
- `type` (String) If application_type is Custom, type can be: Java, Kafka Streams, Pega, SAP, DotNet, Bridge, Python, KSML, Other. If application_type is Connector, type is required: SINK or SOURCE. If application_type is Ksml, this field must be null/omitted. If application_type is FLINK_SQL, leave it out. Use 'Other' when the desired application type is not available in the predefined list.

### Read-Only

- `id` (String) Application unique identifier

## Example Usage

```hcl
resource "axual_application" "dev_dashboard" {
  name    = "DeveloperDashboard"
  application_type     = "Custom"
  short_name = "dev_dash"
  application_id = "io.axual.devs.dashboard"
  owners = axual_group.team-awesome.id
  type = "Java"
  visibility = "Public"
  description = "Dashboard with crucial information for Developers"
  depends_on = [axual_topic_config.logs_in_production, axual_topic.support]
}
```
For a full example which shows the capabilities of the latest TerraForm provider, check https://github.com/Axual/terraform-provider-axual/tree/master/examples/axual.

## Changing `short_name`

Platform Manager refuses a new `short_name` while the application has a principal, a credential or a
deployment that was started, on any environment. Access grants alone do not block it.

To change `short_name` in one apply, add this `lifecycle` block to each `axual_application_principal`,
`axual_application_credential` and `axual_application_deployment` of the application:

```hcl
resource "axual_application_principal" "dev_dashboard" {
  environment = axual_environment.development.id
  application = axual_application.dev_dashboard.id
  principal   = file("certs/dev_dashboard.cer")

  lifecycle {
    replace_triggered_by = [axual_application.dev_dashboard.short_name]
  }
}
```

When `short_name` changes, Terraform deletes these resources, then changes the application, then creates
them again. Terraform always runs the deletes first, because these resources depend on the application.

The block acts only when `short_name` changes. Adding it or removing it shows "No changes" in the plan,
and a change of any other attribute replaces nothing. So you can keep it, or add it in the same change as
the new `short_name` and remove it after that apply.

- A principal is created again with the same certificate. This also works when the instance prevents
  certificate reuse.
- A credential is created again with a new username and password. Give them to the application.
- A deployment is stopped, deleted, created again and started.
- Do not set `create_before_destroy` on these resources: the old ones must be gone before the application
  can change.

Platform Manager does not delete the last principal of an application on an environment where the
application has a pending or approved access grant, unless the application keeps a Kafka credential there.
A credential that is replaced in the same apply does not count: Terraform may delete it first. So when the
application has grants:

- If the application also has an `axual_application_credential` with `target = "KAFKA"` on that
  environment, add `depends_on = [axual_application_credential.<name>]` to the principal. Terraform then
  deletes the principal before the credential, and the grants stay approved.
- Otherwise add the same `lifecycle` block to the `axual_application_access_grant`, and let it depend on
  the principal (`depends_on`). The grant is revoked and requested again. In an environment where the topic
  owner approves grants, the new request stays Pending until it is approved again. A decision with
  `grant_id = axual_application_access_grant.<name>.id` in the same configuration approves it in the same
  apply, with no extra block. A decision by name or UID needs the `lifecycle` block and
  `depends_on = [axual_application_access_grant.<name>]`. Replacing the decision does no harm here: the grant
  is revoked and requested again anyway, and the new decision approves the new request.

For a one-off rename without `lifecycle` blocks, run `terraform apply -replace=<address>` for each
principal, credential and deployment of the application, in the same apply as the new `short_name`
(with a saved plan: `terraform plan -replace=<address> -out=tfplan`, then `terraform apply tfplan`). With
`count` or `for_each`, name each instance and put the whole argument in single quotes, for example
`-replace='axual_application_principal.dev_dashboard["dev"]'`: an address without the key replaces
nothing, and the apply then fails. With grants, the rules above still apply: add the `depends_on`, or also
replace the grants, and the decisions by name or UID that approve them (a decision with `grant_id` is
replaced by itself).

For a production application whose grants must not be revoked, create a new application with the new
`short_name` instead. Get its grants approved, move the clients to it, and then delete the old application.

## Import

Import is supported by ID, or by name (`name:`):

```shell
terraform import axual_application.<LOCAL NAME> <APPLICATION UID>
terraform import axual_application.test_application b21cf1d63a55436391463cee3f56e393
terraform import axual_application.<LOCAL NAME> name:<APPLICATION NAME>
terraform import axual_application.test_application 'name:payments-producer'
```

The name must match exactly, case included. An `import` block (Terraform 1.5 or later) takes the same IDs:

```terraform
import {
  to = axual_application.test_application
  id = "name:payments-producer"
}
```

In Terraform 1.12 or later, an `import` block can use `identity` instead of `id`:

```terraform
import {
  to = axual_application.example
  identity = {
    id = "b21cf1d63a55436391463cee3f56e393"
  }
}
```
