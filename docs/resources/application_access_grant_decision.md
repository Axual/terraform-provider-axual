# axual_application_access_grant_decision (Resource)

The topic team's decision about one application's access to a topic in an environment. `APPROVED` approves every request from the application, now and later. `DENIED` rejects or revokes, also every later request. A reject or revoke in the UI under `APPROVED` lasts only until the next request. Nothing about the grant's status fails a plan. Read more: https://registry.terraform.io/providers/Axual/axual/latest/docs/guides/manage-application-access-to-topics

Use it in the topic team's repository. The application team requests access with `axual_application_access_grant` in its own repository; the two repositories can apply in either order. It replaces `axual_application_access_grant_approval` and `axual_application_access_grant_rejection`.

## Three rules

1. **The topic team writes `decision`.** `APPROVED` approves every request from that application, now and later. `DENIED` (with a `reason`) rejects or revokes, also every later request.
2. **The application team changes `request_again` to ask again.** The text isn't sent to the platform, so explain the reason in the PR to the topic repository. After `DENIED`, the topic team changes the decision first.
3. **Removing a decision doesn't revoke**, unless `revoke_on_destroy = true`. A block moved from an old `_approval` keeps `true`.

## What the provider does

| Grant status | `decision = "APPROVED"` | `decision = "DENIED"` |
|---|---|---|
| `Not found` (no request yet) | Nothing; one warning per topic and environment names the decisions that wait | Nothing |
| `Pending` | **Approve** | **Reject** with `reason` |
| `Approved` | Nothing | **Revoke** with `reason` |
| `Rejected`, `Revoked`, `Cancelled` | Nothing; a warning when the grant was closed outside Terraform | Nothing |

That's the whole rule. It looks only at the grant's status, never at who closed it, so nothing the application team does can get around a `DENIED`. A request made again is handled like a first request.

The provider approves only when the platform offers approve to the signed-in user. Without it (for example when self-approval is disabled and this user made the request), the plan warns and plans no change; approve in the UI as another topic owner. Reject and revoke are always tried.

An action on an existing block shows in the plan as an in-place change of `current_status`, for example `current_status = "Pending" -> "Approved"`. A new block shows `(known after apply)` and a warning that names the action. Every approval names the application's owner group, so you can check that a decision by name approves the team you mean. Nothing about the grant's status fails a plan.

The apply checks the grant again before it acts. If it already reached the planned status (for example the application team revoked it itself before a planned revoke), the apply does nothing and succeeds with a warning. If it changed in another way since the plan, the apply fails with "The grant changed between plan and apply" and changes nothing; run plan again.

The decision finds its grant by `grant_id` first, then by application UID, then by name, so a renamed application keeps its decision; the plan warns until `application` is updated. A decision for an application name that doesn't exist warns "No application named … found (yet)".

## Required Roles
- STREAM_ADMIN or be part of the Team that owns the Topic

## Schema

### Required

- `decision` (String) `APPROVED` approves every `Pending` request from the application, also one made again after a reject or revoke. `DENIED` rejects a `Pending` request and revokes an `Approved` grant. The provider never approves under `DENIED`.

### Optional

- `access_type` (String) `CONSUMER` or `PRODUCER`. See `application`.
- `application` (String) Application UID or name. The grant is found among the grants on the topic, also before the request exists. Set `application`, `topic`, `environment` and `access_type` (multi-repo), or `grant_id` (single repository); with `grant_id` they are filled from the grant.
- `environment` (String) Environment UID. See `application`.
- `grant_id` (String) The grant UID. In a single repository, set it to `axual_application_access_grant.x.id` instead of the four lookup attributes; changing it replaces the block. Both together, as `terraform plan -generate-config-out` writes them, must point at the same grant. Otherwise the provider fills it in: null until the application team requests access, and it changes when the application is created again.
- `reason` (String) Required when `decision = "DENIED"`. Sent with the reject or revoke; the application team reads it as `decision_reason`.
- `revoke_on_destroy` (Boolean) When `true`, removing the block revokes an `Approved` grant. Default `false`: removing the block only stops managing the decision.
- `topic` (String) Topic UID. See `application`.

### Read-Only

- `closed_outside_terraform` (Boolean) `true` when `decision = "APPROVED"` and the grant was rejected or revoked outside Terraform, for example in the UI: the next request will be approved. Not set by this decision's own reject or revoke, nor when the application team gave up access itself (the user who requested it closed it); with one account for both teams a revoke in the UI looks like that and isn't reported. Under `DENIED` a rejected or revoked grant counts as this decision's own close, so the flip to `APPROVED` isn't reported; a decision imported or moved as `APPROVED` onto a closed grant reports it. Use it in a `check` block. It only reports; it never changes what the provider does.
- `current_status` (String) The grant's status: `Pending`, `Approved`, `Rejected`, `Revoked`, `Cancelled`, or `Not found` when there is no request that this user can see.
- `id` (String) `<topic>/<environment>/<access_type>/<application>`, set at create and never changed. Import accepts it, or a grant UID.

## Example Usage

Topic repository, one block for all decisions on a topic and environment, and a `check` that lists what needs the topic team:

```terraform
locals {
  logs_dev_consumers = {
    "Log Scraper" = { decision = "APPROVED" }
    "POC Secret"  = { decision = "DENIED", reason = "Not allowed to read logs, see INC-1234" }
  }
}

resource "axual_application_access_grant_decision" "logs_dev_consumers" {
  for_each    = local.logs_dev_consumers
  application = each.key
  topic       = axual_topic.logs.id
  environment = data.axual_environment.dev.id
  access_type = "CONSUMER"
  decision    = each.value.decision
  reason      = try(each.value.reason, null)
}

# Every waiting request, also from applications that have no decision yet,
# and every grant closed outside Terraform while the decision is still APPROVED.
check "logs_dev_grants" {
  data "axual_application_access_grants" "pending" {
    topic       = axual_topic.logs.id
    environment = data.axual_environment.dev.id
    statuses    = ["Pending"]
  }
  assert {
    condition     = length(data.axual_application_access_grants.pending.grants) == 0
    error_message = "Waiting for the topic team: ${join(", ", [for g in data.axual_application_access_grants.pending.grants : g.application_name])}"
  }
  assert {
    condition     = alltrue([for d in axual_application_access_grant_decision.logs_dev_consumers : !d.closed_outside_terraform])
    error_message = "Closed outside Terraform, the next request will be approved: ${join(", ", [for k, d in axual_application_access_grant_decision.logs_dev_consumers : k if d.closed_outside_terraform])}. To keep it closed, set decision = \"DENIED\" with a reason."
  }
}
```

**A failing `check` is only a warning.** Plan and apply still succeed, and the exit code stays 0, so one grant that changed outside Terraform doesn't block unrelated PRs. For a hard signal, run a scheduled drift job, for example an hourly `terraform plan` that alerts when a check fails (like the drift detection in Terraform Cloud or Spacelift). The `check` reads the grants at plan time, so in the run that approves a request it can still list it once.

Single repository, where the same team requests and decides: point the decision at the grant with `grant_id`.

```terraform
resource "axual_application_access_grant_decision" "log_scraper" {
  grant_id = axual_application_access_grant.log_scraper_reads_logs.id
  decision = "APPROVED"
}
```

With `grant_id`, the provider fills `application`, `topic`, `environment` and `access_type` from the grant; set either `grant_id` or all four of them. Changing `grant_id` replaces the block.

## Revoking

To revoke so that it lasts, set `decision = "DENIED"` with a `reason` in the topic repository. A reject or revoke in the UI works too, but under `APPROVED` it lasts only until the next request: the topic repository's next apply after a request approves it again. Until then every topic plan warns, and `closed_outside_terraform` is `true`.

To cut access now:

1. Revoke the grant in the UI.
2. Open a PR in the topic repository with `decision = "DENIED"` and the reason.

## Getting access back

| How the grant was closed | What to do |
|---|---|
| The topic team's `DENIED` | **Topic team first:** change `decision` to `"APPROVED"` in a PR. Then the application team asks again (`request_again`), and the topic repository's next apply approves it. If the application team asks first, any topic apply rejects the new request again, with a warning. |
| A reject or revoke in the UI (or by an admin) under `APPROVED` | The application team asks again; the topic repository's next apply approves it. |
| The application team's own cancel or revoke | The application team asks again (adds the grant back, or changes `request_again`); the topic repository's next apply approves it. |

`request_again` text isn't sent to the platform: explain why access is needed in the PR to the topic repository.

## closed_outside_terraform

`true` when `decision = "APPROVED"` and the grant is `Rejected` or `Revoked`, but not by this decision's own apply and not by the application team giving up access (the user who requested the grant closed it). Then the next request will be approved, which may not be what whoever closed it wanted. It only reports; it never changes what the provider does.

- After a flip from `DENIED` to `APPROVED` the grant is still closed by the decision's own reject or revoke: not reported.
- The provider records its own last close in private state. After an import or a `moved` block there is no record yet, so a closed grant is reported until it's requested again.
- With one account for both teams, a revoke in the UI by that account looks like the application team giving up access and isn't reported. Use separate accounts, and revoke as described above.

## Removing a block, or pointing it at another grant

- Removing the block makes no API call, so an `Approved` grant stays `Approved`; the plan warns. Set `decision = "DENIED"` first to revoke, or set `revoke_on_destroy = true`.
- Changing `application` from a name to a UID (or the reverse) is an in-place update without an action.
- Changing `application`, `topic`, `environment`, `access_type` or `grant_id` to another grant replaces the block. The plan warns that the old grant stays `Approved`.

## The id

`id` is `<topic>/<environment>/<access_type>/<application>` with the values the block was created (or imported) with, and it never changes. After you change `application` from a name to a UID, `id` still contains the name. That is expected: `grant_id` holds the grant UID.

## One decision per grant

Keep one decision block per grant. When two decisions in one run point at the same grant (for example one by name and one by UID), the plan warns.

## Auto environments

In an Auto environment the platform approves every request straight away. `decision = "DENIED"` revokes, but the next request is approved again, and every plan warns about it.

## Platform Manager versions

| Platform Manager | Support |
|---|---|
| 15.0.3 and later, 16.x | Public and private applications |
| 15.0.1 to 15.0.2 | Public applications. The requests of private applications aren't visible to the topic owner and show as `Not found`; the warning says the application may be private. Approve those in the UI, or upgrade. |
| Any version with IAM-managed groups | A topic owner who is a member of the owner group only through the IAM doesn't see its requests (a known Platform Manager issue): they show as `Not found`, and the warning names this cause. Run the topic repository as a service account (service accounts keep their membership), set `grant_id`, or approve in the UI. |

A private environment always uses the Auto authorization issuer, so its requests are approved straight away and need no decision.

## Import

By `<topic>/<environment>/<access_type>/<application>` or by grant UID:

```shell
terraform import axual_application_access_grant_decision.example 4fa97a80527f4977befe91ce80893621/b10456f91c634e2aadbc3ad64b20f10b/CONSUMER/Log\ Scraper
terraform import axual_application_access_grant_decision.example a7b9346f4e9a49ebb6934553dbc246c3
```

The first plan after an import sets `decision` from the configuration and acts on it like any plan: under `APPROVED` it approves a `Pending` request. A grant that is `Rejected` or `Revoked` shows `closed_outside_terraform = true` after an import under `APPROVED`: check whether it should stay closed, and set `DENIED` if so.

`terraform plan -generate-config-out` writes `decision = null`: set `decision` (and `reason` for `DENIED`) before you plan. The provider doesn't guess it from the grant's status, because a grant the application team revoked itself would become `DENIED`. The generated block has both `grant_id` and the four lookup attributes; that works, as they point at the same grant. Keep one of the two forms if you like.

In Terraform 1.12 or later, an `import` block can use `identity`:

```terraform
import {
  to = axual_application_access_grant_decision.example
  identity = {
    topic       = "4fa97a80527f4977befe91ce80893621"
    environment = "b10456f91c634e2aadbc3ad64b20f10b"
    access_type = "CONSUMER"
    application = "Log Scraper"
  }
}
```

## Moving from the approval and rejection resources

Terraform 1.8 or later:

```terraform
moved {
  from = axual_application_access_grant_approval.log_scraper
  to   = axual_application_access_grant_decision.log_scraper
}

resource "axual_application_access_grant_decision" "log_scraper" {
  application = "Log Scraper"
  topic       = axual_topic.logs.id
  environment = data.axual_environment.dev.id
  access_type = "CONSUMER"
  decision    = "APPROVED"
  revoke_on_destroy = true # keeps today's behaviour: removing this block revokes
}
```

In a single repository, the moved block can use `grant_id = axual_application_access_grant.log_scraper_reads_logs.id` instead of the four lookup attributes.

The plan shows the move, and no API action. When `application` is a UID (for example taken from the grant), the first plan also changes it from the name to the UID, in place. A moved `_approval` keeps `revoke_on_destroy = true`, so removing the block still revokes, as before. Without `revoke_on_destroy = true` in the configuration, the migration plan shows `revoke_on_destroy = true -> false`: accept it only if removing a decision should no longer revoke. A moved `_rejection` gets `decision = "DENIED"` and keeps its reason.

For Terraform before 1.8, use a `removed` block with `lifecycle { destroy = false }` for the old resource (Terraform 1.7) and an `import` block for the new one. Don't delete the old approval: that revokes the grant.
